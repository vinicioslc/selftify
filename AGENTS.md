# Selftify — Architecture & Development Guide

> **Personal developer notes** (legal references, restrictions, etc.) are kept in `USER_INSTRUCTIONS.md` (gitignored). See there before contributing.

## Overview

Cross-platform music player targeting **Android** and **Desktop** (Linux/macOS/Windows) with support for:

| Source     | Type         | Auth Method                  |
|------------|--------------|------------------------------|
| YouTube Music | InnerTube (youtubei.js) | Browser cookies (Netscape format) |
| Local Files | MP3 scan     | Platform fs access (Electron / Capacitor) |

Built with **React 19 + TypeScript + Vite + Tailwind CSS v3 + shadcn/ui** on **Electron** (desktop) + **Capacitor** (Android).

## Architecture Decisions

### 1. Electron + Capacitor over alternatives

| Aspect | Electron + Capacitor | Tauri |
|--------|----------------------|-------|
| Android | ✅ via Capacitor | ✅ |
| Desktop | ✅ via Electron | ✅ |
| Node.js access | ✅ (Electron main process) | ❌ (Rust backend) |
| Native libs | ✅ better-sqlite3, music-metadata | ❌ |
| Development speed | ✅ Fast iteration | ❌ Cross-language debugging |

### 2. Web Audio API for audio playback

All audio goes through the browser's `<audio>` element, connected to an `AudioContext` via `createMediaElementSource()`. This gives us:

- The `AnalyserNode` for visualizers (butterchurn, audiomotion)
- Cross-platform compatibility (mobile + desktop)
- No native audio plugins needed

The `WebAudioProvider` component wraps the app and manages:

- `Audio` element lifecycle
- `AnalyserNode` for visualizer data
- Play/pause, seek, volume via React state → audio element
- Track loading via `controller.getStreamUrl()`

### 3. Controller Pattern (Strategy)

```
┌───────────────────────────────────────────────────┐
│                  App.tsx                           │
│  getController() → ServerController               │
├───────────────────────────────────────────────────┤
│  ServerController interface:                      │
│  ─ search()                                       │
│  ─ getAlbumDetail() / getAlbumList()              │
│  ─ getAlbumArtistDetail() / getAlbumArtistList()  │
│  ─ getSongDetail() / getSongList()                │
│  ─ getPlaylistDetail() / getPlaylistList()         │
│  ─ getStreamUrl() / getImageUrl()                  │
├──────────────────────┬────────────────────────────┤
│   YouTube Controller  │   Local Controller         │
└──────────────────────┴────────────────────────────┘
```

Each controller translates its source's native API into the shared `Song`, `Album`, `AlbumArtist` domain types.

### 4. Zustand over Context

All global state uses Zustand with `persist` middleware (localStorage):

- **`auth.store`**: Origin list + credentials
- **`player.store`**: Queue, current track, playback state
- **`settings.store`**: Theme, visualizer, playback preferences

### 5. Visualizers

Two engines, selectable in Settings:

| Engine | Description | GPU | Bundle impact |
|--------|-------------|-----|---------------|
| **Butterchurn** | MilkDrop-style (Winamp) | Heavy (WebGL) | ~840 KB |
| **AudioMotion** | Spectrum analyzer bars | Light (Canvas) | ~30 KB |
| **None** | Disabled | None | 0 KB |

Both read frequency data from the shared `AnalyserNode` exposed by `WebAudioProvider`.

## Platform-Specific Notes

### Android (Capacitor)

- Audio continues in background via `Audio` element in WebView
- File picker for local music: Capacitor Filesystem plugin
- Touch targets: minimum 44x44 dp (shadcn defaults handle this)
- Bottom player bar is smaller on mobile (72px vs 90px)
- Full-screen player acts as the primary mobile "now playing" screen

### Desktop (Electron)

- Keyboard shortcuts: space (play/pause), arrows (seek/next/prev)
- System media keys: Electron handles via globalShortcut API
- Resizable window with min 480x600
- Sidebar collapse for space efficiency
- File system access via Electron IPC (preload bridge)

### Web

- The app can also run as a plain web app via `npm run dev:web`
- Local file access limited to browser `<input type="file">`
- Stream URLs must be CORS-compatible for web use
- Some Electron/Capacitor features (file system, native dialogs) unavailable

## Spec Conventions & Agent Roles

When a new feature or behavior change is proposed, create spec files under `specs/` following this naming:

```
specs/
├── <feature-name>.md          # General / technical spec
├── <feature-name>.ui.md       # UX/UI behavior (designer perspective)
└── <feature-name>.api.md      # API contracts, data flows, types
```

A spec may have only `.md` and `.ui.md`, or all three — depending on scope.

### `<name>.md` — General / Technical Spec

Created by: **developer** or **general agent** (audience: engineers)

Contents:

- Problem statement, architecture decisions, component tree
- Props / state changes, files changed with line-level detail
- Edge cases, error states, migration notes

### `<name>.ui.md` — UX/UI Spec

Created by: **UI-UX agent** (audience: designers, product, front-end)

Contents:

- Visual layout, states per component (default, hover, active, disabled, empty, error)
- Animation timing & curves, user flows, responsive behavior
- Consistency rules (shapes, spacing, typography), accessibility

Task prompt template:

```
Create <feature-name>.ui.md for the <feature-name> spec.
Focus on: user-facing behavior, visual states, layout,
animation, user flows, responsive rules, consistency.

Do NOT include code, file paths, props, or implementation details.
Write from a UX designer's perspective.
Base it on the problem description in <feature-name>.md.
```

### `<name>.api.md` — API & Data Spec

Created by: **API / Data agent** (audience: backend, state management)

Contents:

- Controller methods (inputs, outputs, error codes)
- Store slices (state shape, actions, selectors)
- Data transformations, DB queries, caching strategy, offline/error handling

Task prompt template:

```
Create <feature-name>.api.md for the <feature-name> spec.
Focus on: controller interface, store state shape,
data transformations, DB queries, error handling, caching.

Include type signatures where relevant.
Base it on the problem description in <feature-name>.md.
```

### Workflow

```
1. Problem identified
       │
       ▼
2. <feature-name>.md  ─── created by developer / general agent
       │
       ├──► UI-UX agent ───> <feature-name>.ui.md
       │
       └──► API/Data agent ───> <feature-name>.api.md
       │
       ▼
3. Implementation begins (all three specs as reference)
```

The `.md` file is the **source of truth** for scope. The `.ui.md` and `.api.md` files derive from it and should be kept in sync.

### Spec-First Rule

**Toda adição de código deve ser pautada em alguma spec.** Antes de implementar qualquer funcionalidade, comportamento, ou mudança de API:

1. Verifique se já existe uma spec que cobre o escopo em `specs/`.
2. Se existir, implemente exatamente o que está especificado. Se o comportamento real divergir do spec, atualize o spec primeiro.
3. Se **não** existir spec para o que está sendo implementado, **crie ou atualize a spec mais adequada** antes de escrever código, documentando: problema, solução, tipos, eventos, arquivos afetados e edge cases.
4. Specs são artefatos vivos — toda descoberta durante implementação que altere o design original deve ser refletida na spec correspondente.

A única exceção é refatoração puramente mecânica (renomear variável, extrair função) sem mudança de comportamento visível.

## Design Principles

- **No direct DOM manipulation**: All UI through React state + shadcn components
- **Minimal dependencies**: Only add what's needed
- **TypeScript strict**: Full type safety across API boundaries
- **Mobile-first responsive**: Tailwind breakpoints for adaptive layout
- **Source-agnostic UI**: Same components work with YouTube or Local
- **Observability**: Console.debug() with `[Selftify]` prefix for API calls
- **User-facing status**: Any operation of interest to the user (loading, searching, indexing, playing) must publish a brief message via `useStatusStore.getState().addMessage(text, level, source)` so it appears in the TopBar status popover. Use `"info"` for normal activity, `"success"` for completion, `"warn"` for warnings, `"danger"` for errors. Examples: `"Searching local files..."`, `"Found 42 songs"`, `"Scan complete"`.
- **No cross-project references**: This project must never reference any other self-hosted music projects. See `USER_INSTRUCTIONS.md` for details.

### Shell Layout Architecture

The app uses a CSS Grid shell layout (`src/styles/layout.css`) with four named areas:

```
┌──────────────────────────────────────┐
│              topbar                   │  ← drag region, always on top
│              z-index: 300             │
├──────────────────┬───────────────────┤
│                  │                    │
│     sidebar      │     content        │  ← main content area (scrolls internally)
│                  │                    │
├──────────────────┴───────────────────┤
│   player (bottom bar)                 │  ← always on top of content
│   z-index: 200                       │  │ contains progress bar + controls
└──────────────────────────────────────┘
```

**Rules:**

1. **Topbar (`grid-area: topbar`, `z-index: 300`)** — Always on top of all content. Contains window controls (close, minimize) in Electron and the app navigation/drag region. Uses `-webkit-app-region: drag` for Electron window dragging.

2. **Player bar (`grid-area: player`, `z-index: 200`)** — Always visible at the bottom, above the main content. Contains the playback controls (play/pause, skip, shuffle, repeat), the progress/seek slider (`PlayerbarSlider`), volume control, and queue/lyrics buttons. The progress bar lives inside the player bar (center column) and stretches between the left and right control groups.

3. **Content area** (`main-content` grid) — Stretched vertically between the topbar and player bar. It contains the sidebar + page content. The content fills all available space and scrolls internally per-page (pages use their own scroll containers, NOT `body` scroll).

4. **Modals / Dialogs** — Render via Radix Portal to `document.body`, outside the CSS Grid. The `DialogOverlay` uses `z-[1000]` and `DialogContent` uses `z-[1001]` to always stack above all layout elements.

5. **No body scroll** — `html, body, #root` have `overflow: hidden`. All scrolling is contained within page-level scroll containers inside the grid's content area.

### The `platformFetch` Pattern

When a library (e.g. `youtubei.js`) needs to make HTTP requests from the renderer, you **cannot** use `globalThis.fetch` directly — it will fail on both Electron and Android due to CORS.

Always use a **platform-aware fetch wrapper** that tries these in order:

```ts
async function platformFetch(input, init): Promise<Response> {
  // 1. Electron — routes through IPC to main process (no CORS)
  if (window.electronApi?.yt?.fetch) {
    return electronFetch(input, init);
  }
  // 2. Capacitor/Android — uses native HTTP client (no CORS)
  if (CapacitorHttp?.request) {
    return capacitorFetch(input, init);
  }
  // 3. Web fallback — will have CORS on YouTube endpoints
  return globalThis.fetch(input, init);
}
```

### Serializing `fetch` init objects through IPC

`Headers` and `Uint8Array` are **NOT structured-cloneable** across Electron IPC. Always serialize them:

| Type | IPC-safe format | Reconstruction |
|------|----------------|----------------|
| `Headers` instance | `Record<string, string>` via `.forEach()` | `new Headers(plainObj)` |
| `Uint8Array` / `ArrayBuffer` | `number[]` via `Array.from()` | `Buffer.from(arr)` (Node) or `new Uint8Array(arr)` (browser) |

### CapacitorHttp binary data handling

On Android, `CapacitorHttp.request({ responseType: "arraybuffer" })` returns `data` as a **base64 string**.

```ts
// Request: string body → send as-is; Uint8Array body → base64 + set Content-Type
if (Array.isArray(body)) {
  const bytes = new Uint8Array(body);
  const binary = String.fromCharCode(...bytes);
  reqData = btoa(binary);
  headers["Content-Type"] = "application/x-protobuf";
}

// Response: base64 → Uint8Array
const binaryStr = atob(resp.data);
const bytes = new Uint8Array(binaryStr.length);
for (let i = 0; i < binaryStr.length; i++) bytes[i] = binaryStr.charCodeAt(i);
```

### Capacitor config for external APIs

Always add these to `capacitor.config.json` when making requests to external domains:

```json
{
  "server": {
    "allowNavigation": ["*.youtube.com", "*.ytimg.com", "*.google.com"]
  },
  "plugins": {
    "CapacitorHttp": { "enabled": true }
  }
}
```

- `CapacitorHttp.enabled = true` patches `window.fetch` to use native Android HTTP (bypasses CORS).
- `allowNavigation` lets the WebView load resources from these domains.

### Module-level singleton per platform

For libraries that maintain state (e.g. `youtubei.js` Innertube client), use a module-level singleton pattern:

```ts
let currentInstance: Innertube | null = null;
let currentCookie: string | null = null;

async function getClient(cookie?: string | null): Promise<Innertube> {
  if (currentInstance && currentCookie === cookie) return currentInstance;
  currentInstance = await createClient(cookie);
  currentCookie = cookie;
  return currentInstance;
}
```

This avoids re-authentication on every call and works identically on all platforms because it's pure JS.

### Third-party JS libraries in Capacitor vs Electron

| Library | Electron | Capacitor (Android) |
|---------|----------|---------------------|
| `youtubei.js` (InnerTube) | ✅ Need `platformFetch` (IPC for CORS) | ✅ Need `platformFetch` (CapacitorHttp) |
| `music-metadata` | ✅ Node.js (main process) | ❌ No native bindings |
| `better-sqlite3` | ✅ Node.js (main process) | ❌ No native bindings |
| `yt-dlp` | ✅ Via `child_process` in main | ❌ No system binary |

**Rule of thumb**: If a library depends on Node.js APIs (fs, child_process, native addons), it **only works in Electron**. If it's pure JS/TS with only `fetch`/`Web API`, it can work on both platforms but may need the `platformFetch` wrapper.

## Audio Playback Peculiarities

### YouTube stream URLs have no CORS

`googlevideo.com` (YouTube audio stream) does **NOT** send `Access-Control-Allow-Origin`. When using `AudioContext.createMediaElementSource()` to route an `<audio>` element through an `AnalyserNode` (for visualizers), Chromium **silences** the output for cross-origin media that lacks CORS headers. The `<audio>` element plays fine alone, but once connected via `createMediaElementSource`, **no audio comes out**.

**Solution**: Dual audio elements — one connected to the AudioContext (local files), one standalone (streams).

```ts
// browser-audio-provider.tsx
const audioRef = useRef<HTMLAudioElement | null>(null);       // local → AudioContext
const streamAudioRef = useRef<HTMLAudioElement | null>(null); // stream → direct playback

function isStreamUrl(url: string): boolean {
  return url.startsWith("https://") && !url.startsWith("file://");
}
```

| Element | Connected to AudioContext? | Used for |
|---------|---------------------------|----------|
| `audioRef` | ✅ `createMediaElementSource` → AnalyserNode | Local files (no CORS) |
| `streamAudioRef` | ❌ Direct `<audio>` playback | YouTube streams (googlevideo.com) |

When switching between local and stream, pause the inactive element before loading the active one.

### `resumeContext()` only needed for local files

Only call `audioCtx.resume()` when playing through the AudioContext pipeline. Stream playback via the standalone `<audio>` element doesn't need an AudioContext at all — it plays directly through the browser's audio output. This also avoids autoplay-policy issues since `<audio>.play()` from a user gesture always works.

### yt-dlp stream URLs expire

Each `yt:stream-url` extraction returns a signed URL with an `expire` parameter (~6h from generation). The `ytStreamCache` caches them for 5 minutes (`CACHE_TTL`). Do not cache for longer than that, as expired URLs return 403.

### Sequential yt-dlp operations

The `TaskQueue` in `electron/queue.ts` processes tasks **sequentially** (single-threaded). A play click triggers this chain:

```
MusicBrainz:  play → searchAndRank (yt:search, ~3-10s) → getStreamUrl (yt:stream-url, ~3-5s) → audio
YouTube Pure: play → getStreamUrl (yt:stream-url, ~3-5s) → audio
```

Total time from click to first audible sound: **8–15s** for MusicBrainz, **3–5s** for YouTube Pure. This is expected — yt-dlp must extract the stream URL on-demand. If a task is already running (e.g. a previous search), new tasks queue behind it.

### Audio format of YouTube streams

`yt-dlp --format bestaudio[ext=webm]/bestaudio` returns format **251** (Opus 160kbps in WebM container). Chrome/Chromium/Electron play this natively. Safari does not support WebM audio; macOS Electron users may need a different format strategy.

### Every playback path must resolve `song.path`

Search results, album pages, artist pages, and local file listings each have their own `playSong()` function. When adding stream URL resolution (via `getStreamUrl`), **every** playback path must be updated — not just the search page.

Rules:

- **Local files** already have `song.path` set → `setQueue([song])` is correct.
- **Online songs** (MusicBrainz, YouTube) have `song.path = null` → must call `getStreamUrl(song)` first, then `setQueue([{...song, path: streamUrl}])`.
- **Mixed pages** (album page has local + online songs): check `if (song.path)` before resolving.
- **Play All** must resolve every song individually via `Promise.allSettled`.

Always grep for `setQueue` across the entire codebase when adding/modifying playback to catch all paths:

```bash
grep -rn "setQueue" src/features/ --include="*.tsx"
```

## Data Storage Conventions

### Track paths MUST be relative-to-root and complete

Every `track.path` stored in the SQLite database **must** be the full relative path from the library root, including the artist and album directory. Never strip the directories.

**Correct**: `"Trapt/Amalgamation (1998)/01 - Sound Off.mp3"`
**Wrong**: `"01 - Sound Off.mp3"` (no directory)

Rationale:
- The audio provider always prepends the library root via `resolveLocalPath(path)` → `root + "/" + path`.
- Any path concatenation elsewhere (controllers, services) also assumes relative-to-root.
- A bare filename would produce an invalid absolute path (`/home/user/Music/01 - Sound Off.mp3`), missing the artist/album directories.
- No code should guess or reconstruct album directories (e.g. appending `(Year)`). The stored path is the source of truth.

### File organizer updates the path

When the file organizer runs (`organizeOnScan`), it moves files and updates `track.path` to reflect the new location. After organization, the path still follows the same convention: relative-to-root and complete.

### Scanning sets the initial path

In `local-indexer.ts`, the initial `track.path` assignment must use `getRelativePath(libraryRoot, filePath)` **without stripping directories**. Only strip if the path would exceed the library root:

```ts
// CORRECT: full relative path from library root
track.path = getRelativePath(libraryRoot, filePath)
// → "Artist/Album (Year)/file.mp3"

// WRONG: strips directories, loses location
track.path = getRelativePath(...).replace(`${artistDir}/.../`, "")
// → "file.mp3" — useless without context
```

### Rescan after path changes

If the path storage convention is changed, a full rescan is required to repopulate `track.path` for all existing entries. The database does not auto-migrate old entries. Use the rescan UI button or do a fresh scan after a schema/logic change.

## Recommended Engineering Reasoning Flow

Follow these steps in order when debugging or implementing a feature:

1. **Map the full flow before touching code** — Search (rg) both sides (frontend + backend) to understand ALL points where the feature appears: controller, service, store, validator, routes, component, existing tests.

2. **Read canonical specs and docs** — Before implementing, consult `specs/` (UX, API, UI) and `AGENTS.md` to understand contracts, rules, and project patterns.

3. **Identify the two layers of the problem** — Recognize whether a bug has a backend front (permission/validation exists but is wrong) and a frontend front (UI only disables a button, no real guard) — plan the fix in each.

4. **Verify permissions and authorization** — Check Permission/Role models, seeders, and existing authorization tests to understand who CAN and who CANNOT do the action.

5. **Check the validator contract** — The validator is a common blind spot. Verify whether the field is in the validated schema with the correct values, and whether a silent filter is swallowing the value.

6. **Dig into the concrete bug in the data layer** — Don't accept "it works on the surface." Read the store, API wrapper, and backend return to find the real problem (e.g., wrong unwrap in `update()` that leaves `undefined` in the local cache).

7. **Fix in layers** — Create/alter in this order: (a) functional test describing expected behavior, (b) backend fix if needed, (c) frontend store/api fix, (d) component/UI fix, (e) update the UX spec.

8. **Format and validate** — Run formatter on touched files, then run focused tests before declaring done.

9. **Don't loosen assertions** — If a test fails due to middleware/seed noise, adjust the fixture — not the assertion.

**Summary**: Understand the full flow (data → API → store → UI), find the real cause instead of the symptom, fix in each layer with a corresponding test, and only touch code after reading specs and permissions.
