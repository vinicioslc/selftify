# Selftify — Architecture & Development Guide

> **Personal developer notes** (legal references, restrictions, etc.) are kept in `USER_INSTRUCTIONS.md` (gitignored). See there before contributing.

## Overview

Cross-platform music player targeting **Android** and **Desktop** (Linux/macOS/Windows) with support for:

| Source     | Type         | Auth Method                  |
|------------|--------------|------------------------------|
| YouTube Music | InnerTube (youtubei.js) | Browser cookies (Netscape format) |
| Local Files | MP3 scan     | Platform fs access (Electron / Capacitor) |

Built with **React 19 + TypeScript + Vite + Tailwind CSS v3 + shadcn/ui** on **Electron** (desktop) + **Capacitor** (Android).

## Architecture Decisions

### 1. Electron + Capacitor over alternatives

| Aspect | Electron + Capacitor | Tauri |
|--------|----------------------|-------|
| Android | ✅ via Capacitor | ✅ |
| Desktop | ✅ via Electron | ✅ |
| Node.js access | ✅ (Electron main process) | ❌ (Rust backend) |
| Native libs | ✅ better-sqlite3, music-metadata | ❌ |
| Development speed | ✅ Fast iteration | ❌ Cross-language debugging |

### 2. Web Audio API for audio playback

All audio goes through the browser's `<audio>` element, connected to an `AudioContext` via `createMediaElementSource()`. This gives us:
- The `AnalyserNode` for visualizers (butterchurn, audiomotion)
- Cross-platform compatibility (mobile + desktop)
- No native audio plugins needed

The `WebAudioProvider` component wraps the app and manages:
- `Audio` element lifecycle
- `AnalyserNode` for visualizer data
- Play/pause, seek, volume via React state → audio element
- Track loading via `controller.getStreamUrl()`

### 3. Controller Pattern (Strategy)

```
┌───────────────────────────────────────────────────┐
│                  App.tsx                           │
│  getController() → ServerController               │
├───────────────────────────────────────────────────┤
│  ServerController interface:                      │
│  ─ search()                                       │
│  ─ getAlbumDetail() / getAlbumList()              │
│  ─ getAlbumArtistDetail() / getAlbumArtistList()  │
│  ─ getSongDetail() / getSongList()                │
│  ─ getPlaylistDetail() / getPlaylistList()         │
│  ─ getStreamUrl() / getImageUrl()                  │
├──────────────────────┬────────────────────────────┤
│   YouTube Controller  │   Local Controller         │
└──────────────────────┴────────────────────────────┘
```

Each controller translates its source's native API into the shared `Song`, `Album`, `AlbumArtist` domain types.

### 4. Zustand over Context

All global state uses Zustand with `persist` middleware (localStorage):
- **`auth.store`**: Origin list + credentials
- **`player.store`**: Queue, current track, playback state
- **`settings.store`**: Theme, visualizer, playback preferences

### 5. Visualizers

Two engines, selectable in Settings:

| Engine | Description | GPU | Bundle impact |
|--------|-------------|-----|---------------|
| **Butterchurn** | MilkDrop-style (Winamp) | Heavy (WebGL) | ~840 KB |
| **AudioMotion** | Spectrum analyzer bars | Light (Canvas) | ~30 KB |
| **None** | Disabled | None | 0 KB |

Both read frequency data from the shared `AnalyserNode` exposed by `WebAudioProvider`.

## Platform-Specific Notes

### Android (Capacitor)

- Audio continues in background via `Audio` element in WebView
- File picker for local music: Capacitor Filesystem plugin
- Touch targets: minimum 44x44 dp (shadcn defaults handle this)
- Bottom player bar is smaller on mobile (72px vs 90px)
- Full-screen player acts as the primary mobile "now playing" screen

### Desktop (Electron)

- Keyboard shortcuts: space (play/pause), arrows (seek/next/prev)
- System media keys: Electron handles via globalShortcut API
- Resizable window with min 480x600
- Sidebar collapse for space efficiency
- File system access via Electron IPC (preload bridge)

### Web

- The app can also run as a plain web app via `npm run dev:web`
- Local file access limited to browser `<input type="file">`
- Stream URLs must be CORS-compatible for web use
- Some Electron/Capacitor features (file system, native dialogs) unavailable

## Spec Conventions & Agent Roles

When a new feature or behavior change is proposed, create spec files under `specs/` following this naming:

```
specs/
├── <feature-name>.md          # General / technical spec
├── <feature-name>.ui.md       # UX/UI behavior (designer perspective)
└── <feature-name>.api.md      # API contracts, data flows, types
```

A spec may have only `.md` and `.ui.md`, or all three — depending on scope.

### `<name>.md` — General / Technical Spec

Created by: **developer** or **general agent** (audience: engineers)

Contents:
- Problem statement, architecture decisions, component tree
- Props / state changes, files changed with line-level detail
- Edge cases, error states, migration notes

### `<name>.ui.md` — UX/UI Spec

Created by: **UI-UX agent** (audience: designers, product, front-end)

Contents:
- Visual layout, states per component (default, hover, active, disabled, empty, error)
- Animation timing & curves, user flows, responsive behavior
- Consistency rules (shapes, spacing, typography), accessibility

Task prompt template:

```
Create <feature-name>.ui.md for the <feature-name> spec.
Focus on: user-facing behavior, visual states, layout,
animation, user flows, responsive rules, consistency.

Do NOT include code, file paths, props, or implementation details.
Write from a UX designer's perspective.
Base it on the problem description in <feature-name>.md.
```

### `<name>.api.md` — API & Data Spec

Created by: **API / Data agent** (audience: backend, state management)

Contents:
- Controller methods (inputs, outputs, error codes)
- Store slices (state shape, actions, selectors)
- Data transformations, DB queries, caching strategy, offline/error handling

Task prompt template:

```
Create <feature-name>.api.md for the <feature-name> spec.
Focus on: controller interface, store state shape,
data transformations, DB queries, error handling, caching.

Include type signatures where relevant.
Base it on the problem description in <feature-name>.md.
```

### Workflow

```
1. Problem identified
       │
       ▼
2. <feature-name>.md  ─── created by developer / general agent
       │
       ├──► UI-UX agent ───> <feature-name>.ui.md
       │
       └──► API/Data agent ───> <feature-name>.api.md
       │
       ▼
3. Implementation begins (all three specs as reference)
```

The `.md` file is the **source of truth** for scope. The `.ui.md` and `.api.md` files derive from it and should be kept in sync.

## Design Principles

- **No direct DOM manipulation**: All UI through React state + shadcn components
- **Minimal dependencies**: Only add what's needed
- **TypeScript strict**: Full type safety across API boundaries
- **Mobile-first responsive**: Tailwind breakpoints for adaptive layout
- **Source-agnostic UI**: Same components work with YouTube or Local
- **Observability**: Console.debug() with `[Selftify]` prefix for API calls
- **User-facing status**: Any operation of interest to the user (loading, searching, indexing, playing) must publish a brief message via `useStatusStore.getState().addMessage(text, level, source)` so it appears in the TopBar status popover. Use `"info"` for normal activity, `"success"` for completion, `"warn"` for warnings, `"danger"` for errors. Examples: `"Searching local files..."`, `"Found 42 songs"`, `"Scan complete"`.
- **No cross-project references**: This project must never reference any other self-hosted music projects. See `USER_INSTRUCTIONS.md` for details.

## Cross-Platform Patterns (Electron + Capacitor Android)

### The `platformFetch` Pattern

When a library (e.g. `youtubei.js`) needs to make HTTP requests from the renderer, you **cannot** use `globalThis.fetch` directly — it will fail on both Electron and Android due to CORS.

Always use a **platform-aware fetch wrapper** that tries these in order:

```ts
async function platformFetch(input, init): Promise<Response> {
  // 1. Electron — routes through IPC to main process (no CORS)
  if (window.electronApi?.yt?.fetch) {
    return electronFetch(input, init);
  }
  // 2. Capacitor/Android — uses native HTTP client (no CORS)
  if (CapacitorHttp?.request) {
    return capacitorFetch(input, init);
  }
  // 3. Web fallback — will have CORS on YouTube endpoints
  return globalThis.fetch(input, init);
}
```

### Serializing `fetch` init objects through IPC

`Headers` and `Uint8Array` are **NOT structured-cloneable** across Electron IPC. Always serialize them:

| Type | IPC-safe format | Reconstruction |
|------|----------------|----------------|
| `Headers` instance | `Record<string, string>` via `.forEach()` | `new Headers(plainObj)` |
| `Uint8Array` / `ArrayBuffer` | `number[]` via `Array.from()` | `Buffer.from(arr)` (Node) or `new Uint8Array(arr)` (browser) |

### CapacitorHttp binary data handling

On Android, `CapacitorHttp.request({ responseType: "arraybuffer" })` returns `data` as a **base64 string**.

```ts
// Request: string body → send as-is; Uint8Array body → base64 + set Content-Type
if (Array.isArray(body)) {
  const bytes = new Uint8Array(body);
  const binary = String.fromCharCode(...bytes);
  reqData = btoa(binary);
  headers["Content-Type"] = "application/x-protobuf";
}

// Response: base64 → Uint8Array
const binaryStr = atob(resp.data);
const bytes = new Uint8Array(binaryStr.length);
for (let i = 0; i < binaryStr.length; i++) bytes[i] = binaryStr.charCodeAt(i);
```

### Capacitor config for external APIs

Always add these to `capacitor.config.json` when making requests to external domains:

```json
{
  "server": {
    "allowNavigation": ["*.youtube.com", "*.ytimg.com", "*.google.com"]
  },
  "plugins": {
    "CapacitorHttp": { "enabled": true }
  }
}
```

- `CapacitorHttp.enabled = true` patches `window.fetch` to use native Android HTTP (bypasses CORS).
- `allowNavigation` lets the WebView load resources from these domains.

### Module-level singleton per platform

For libraries that maintain state (e.g. `youtubei.js` Innertube client), use a module-level singleton pattern:

```ts
let currentInstance: Innertube | null = null;
let currentCookie: string | null = null;

async function getClient(cookie?: string | null): Promise<Innertube> {
  if (currentInstance && currentCookie === cookie) return currentInstance;
  currentInstance = await createClient(cookie);
  currentCookie = cookie;
  return currentInstance;
}
```

This avoids re-authentication on every call and works identically on all platforms because it's pure JS.

### Third-party JS libraries in Capacitor vs Electron

| Library | Electron | Capacitor (Android) |
|---------|----------|---------------------|
| `youtubei.js` (InnerTube) | ✅ Need `platformFetch` (IPC for CORS) | ✅ Need `platformFetch` (CapacitorHttp) |
| `music-metadata` | ✅ Node.js (main process) | ❌ No native bindings |
| `better-sqlite3` | ✅ Node.js (main process) | ❌ No native bindings |
| `yt-dlp` | ✅ Via `child_process` in main | ❌ No system binary |

**Rule of thumb**: If a library depends on Node.js APIs (fs, child_process, native addons), it **only works in Electron**. If it's pure JS/TS with only `fetch`/`Web API`, it can work on both platforms but may need the `platformFetch` wrapper.
